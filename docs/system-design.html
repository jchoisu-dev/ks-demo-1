System design · Demo project 01

KS28 Lottery Platform

A real-time "28"-style lottery game. Results are scraped from public draw feeds every few seconds. Players bet over a single encrypted WebSocket, the platform settles each round automatically, and payouts reach every connected client within the same second.

8 services 12 PM2 processes 1 Redis, 6 logical DBs MariaDB system of record 5 scraped feeds + 2 house-drawn games Node.js · Express · ws · Sequelize · React

Architecture

A round, from draw to payout

  1. Tick. The scraper holds no cron. It sets run_get_number with a 5-second TTL, and Redis keyspace notifications (__keyevent@10__:expired) wake it up. The same trick, on db11, fires a timer at each game's scheduled draw time.
  2. Fetch and dedupe. Each feed is parsed with cheerio. A draw is new only if its period number is greater than game_list_{game}, so repeated scrapes are harmless.
  3. Record the round. lottery_in receives the draw and queues it. lottery_open pops it, updates history and the next four rounds' bet slips, and pushes a settlement job. lottery_qun uses expiring keys to announce "betting closed" to each game room before the draw.
  4. Settle. bet_open loads every open bet for that period, evaluates each one against the result with the current odds and the per-round payout cap (GameSet.max-open), then writes wins, losses and balance changes.
  5. Push. Results go out on sd28-user-room. Every gateway process is subscribed and forwards a message only to the socket whose uuidkey matches. Room-wide events (new draw, countdown) go on sd28-site-room to everyone.

Connecting a client

No session cookie and no REST API. A client asks for a short-lived signed URL, opens one WebSocket with it, and then sends every request as a controller/action message on that socket.

Key decisions

Redis as the only integration point

Services never call each other. They push to a list, publish to a channel, or set a key.

Any worker can restart without the others noticing, and adding a game means adding a scraper and a settlement rule, not a new API.

Writes through a queue, reads direct

Gateways read MariaDB for pages but hand every balance change to async_center via sd28_sub_do_list.

One consumer applies money movements in order, so two simultaneous bets from one user cannot race on the same balance.

One socket per client

Requests, responses and server push share a single WebSocket, with path-style routing.

Live odds, countdowns and payouts need push anyway. Running everything over one channel removes a second protocol and its auth.

Stateless gateways behind signed URLs

The key service signs a timestamp and nonce; the gateway decrypts it and derives the connection key.

No sticky sessions or shared session store. Nginx spreads upgrades across ports freely.

Ingest isolated from the player host

The scraper originally ran in a separate AWS region and replicated draws into the core Redis.

Scraping traffic, its IP reputation and its failures never touch the host players connect to.

Static front ends off the origin

Both SPAs ship from object storage and a CDN.

The origin's attack surface is two URL shapes. Nginx returns 404 for everything else.

Next iteration

The design holds up. These are the changes that would take it from a working demo to something you would run with real balances, ordered by impact.

Correctness

Idempotent settlement

Record a settlement row per (game, period) under a unique key, and apply all of a round's bet updates and balance changes in one database transaction.

Today a crash halfway through a round leaves some bets settled and the job gone from the list.

Reliability

Redis Streams instead of lists and expiry events

Move the queues to Streams with consumer groups and acknowledgements. Move the timers to delayed jobs (BullMQ or a sorted set).

BRPOP removes a job before it is processed, and keyspace notifications are fire-and-forget: a subscriber that is down misses the tick.

Security

Real session auth over TLS

Replace the XOR frame masking with a signed session token (HMAC or JWT) checked at upgrade, and rely on WSS for confidentiality. Drop TLS 1.0 and 1.1 at Nginx.

Masking hides traffic from casual inspection but is not encryption. The key derivation runs in the browser, where anyone can read it.

Security

Secrets out of the source tree

Signing keys, database credentials, bot tokens and the TLS private key go into environment variables or a secret manager.

Scale

Gateways as processes, not ports

Run the player gateway as a PM2 cluster (N processes on one port, or one port per process) and make the Nginx upstream list match it.

Ten ports in one Node process still run on one CPU core.

Operations

Split Redis by role, add visibility

Use separate instances for durable queues (AOF on) and for cache and pub/sub. Export queue depth, settlement latency per round and scraper freshness per feed.

Six logical DBs share one memory limit, one persistence policy and one failure.
